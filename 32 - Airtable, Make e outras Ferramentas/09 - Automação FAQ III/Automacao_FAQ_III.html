Automação FAQ III
decidir e resistir

A IA devolveu um JSON. Agora o cenário precisa decidir: se encontrou a resposta com confiança alta, a sugestão vai para um revisor; se não encontrou, a pergunta vira um rascunho na FAQ e a equipe é avisada. E precisa resistir: se a IA falhar, se o JSON vier quebrado ou se o Airtable recusar um dado, nenhuma pergunta pode se perder. Nesta aula: Router, filtros de rota, rota de fallback e error handlers.

Conceito01

Do JSON à decisão

Resultado da IACaminhoStatus do atendimento
encontrou = true e confianca = altaRota A: sugestão para revisãoSugerida
Qualquer outro casoRota B (fallback): FAQ precisa crescerSem resposta
A IA rotula, a regra decide

É o mesmo princípio do If/else do módulo 31: o modelo devolve campos estruturados; quem escolhe o caminho é uma condição fixa, previsível e fácil de auditar.

Confiança "baixa" vai para a rota B de propósito: é melhor a equipe escrever uma resposta boa do que aprovar uma resposta meia-boca.
Passo 102

O Router

1
Remova o Update provisório da aula 08 (o do if).
2
Depois do Parse JSON, adicione Flow Control · Router.
3
Crie duas rotas, saindo do Router.
4
Na primeira, um filtro; na segunda, marque fallback route.
Como o Router processa

Cada bundle é enviado às rotas na ordem em que estão configuradas; cada rota tem seu filtro. Uma rota marcada como fallback só recebe o bundle se nenhuma outra rota o aceitou.

Sem fallback, um bundle que não passa em nenhum filtro simplesmente para, em silêncio. O atendimento ficaria como "Novo" para sempre.
Passo 203

Os filtros das rotas

// Rota A · "Encontrou com confiança" Condição 1 6. encontrou Boolean operators: Equal to true AND Condição 2 6. confianca Text operators: Equal to alta AND Condição 3 6. resposta Basic operators: Exists // Rota B · "Sem resposta" Fallback route: ✓ (sem condições)
A terceira condição

"resposta existe" é uma trava extra: se a IA disser que encontrou, mas devolver resposta vazia, o caso vai para a equipe, e não para o revisor como se estivesse pronto.

Os valores vêm do Parse JSON (módulo 6). Se você trocar a ordem dos módulos, confira os números nos filtros.
Passo 304

Rota A: para o revisor

MóduloConfiguração
Airtable · Update a recordAtendimento {{2.ID}}: Status = Sugerida; Resposta sugerida = {{6.resposta}}; FAQ usada = {{6.faq_ids}}
Gmail · Send an emailPara o revisor: "Resposta sugerida aguardando aprovação", com a pergunta e o link para a interface de revisão
Onde o revisor trabalha

Na interface "Painel do Revisor" (aula 03), agora apontando para Atendimentos com Status = Sugerida: lê, ajusta o texto em Resposta final e muda o Status para Aprovado ou Descartado.

O e-mail para o revisor leva a pergunta e o link, não o e-mail do aluno. O revisor vê o que precisa para decidir.
Nada é enviado ao aluno nesta rota. O envio é de outro cenário, que só olha atendimentos Aprovados (aula 10).
Passo 405

Rota B: a FAQ cresce

MóduloConfiguração
Airtable · Update a recordAtendimento: Status = Sem resposta
Airtable · Create a recordEm Perguntas: Pergunta = texto recebido; Status = Rascunho; Origem = Atendimento
Gmail · Send an emailPara a equipe: "Pergunta sem resposta na FAQ", com link para o rascunho
O ciclo virtuoso

Toda pergunta sem resposta vira um rascunho na FAQ. Quando a equipe responder e publicar, a IA passa a encontrar perguntas parecidas. A FAQ aprende com os alunos.

E o aluno dessa pergunta? A equipe responde o atendimento pela interface, preenchendo Resposta final e aprovando: o cenário da aula 10 envia.
O rascunho em Perguntas leva só o texto da pergunta, sem o e-mail. Dados pessoais ficam em Atendimentos.
Desempenho06

Responder ao site antes da IA

Na aula 07, o Webhook response ficava no fim. Com busca, IA e rotas, o cenário pode levar vários segundos, e o site ficaria esperando. Mova o Webhook response para logo depois do Create a record:

WebhookPergunta chega
CreateRegistra "Novo"
ResponseSite já responde
Busca · IA · RouterSeguem sem pressa
O aluno não espera a IA

A mensagem "Recebemos sua pergunta" aparece na hora. A resposta chega por e-mail depois da revisão.

O que vem depois do Webhook response continua rodando normalmente na mesma execução. Se algo falhar ali, o site não fica sabendo, e é para isso que servem os error handlers.

Ferramentas08

Os error handlers

HandlerO que faz (central de ajuda)Quando usar
RetryGuarda a execução como incompleta e permite novas tentativas, automáticas ou manuaisFalhas temporárias: IA fora do ar, 429
SkipIgnora o erro e deixa o cenário processar os próximos bundlesQuando aquele bundle pode ser descartado
ResumeDefine um valor substituto para o módulo que falhou e continuaJSON quebrado → "não encontrou"
CommitPara a execução e mantém o que já foi feitoParar sem desfazer gravações anteriores
RollbackPara a execução e reverte as mudanças, quando os módulos suportamOperações que precisam ser "tudo ou nada"
Para adicionar: botão direito no módulo → Add error handler. A rota de erro aparece tracejada e só roda quando aquele módulo falha.

Operação11

Execuções incompletas

1
No painel do cenário, abra Incomplete executions: cada item mostra o módulo que falhou e o erro.
2
Se a causa era temporária, o Retry tenta sozinho. Se não, corrija (chave, token, prompt).
3
Retome a execução: ela continua do ponto em que parou, com os mesmos dados.
Com Process data in order ligado, uma execução incompleta segura as próximas até ser resolvida. Para a FAQ, deixe desligado: uma pergunta com problema não deve travar as outras.
Uma rotina simples

Uma vez por dia, alguém olha as incompletas e os atendimentos "Novo" com mais de uma hora. Se houver, algo está travado.

Armadilhas13

Erros comuns com rotas e erros

Router sem fallback. Casos não previstos param em silêncio.
Skip na IA. O erro some, e a pergunta também.
Confiança baixa na rota do revisor. Respostas fracas parecem prontas.
Retry sem Store incomplete executions. Não há onde guardar a tentativa.
E-mail do aluno no aviso. Revisor e equipe precisam da pergunta, não do contato.
Responder ao site só no fim. O aluno espera a IA para ver "recebemos".
Quiz de fixação14

Teste o que ficou

A) Para rodar sempre
B) Para receber o bundle quando nenhuma outra rota o aceitou
C) Para tratar erros
D) Para economizar créditos
B. Nenhum caso fica sem caminho.

A) Rota A, para o revisor
B) Rota B: a equipe escreve a resposta e a FAQ ganha um rascunho
C) Direto para o aluno
D) É descartada
B. Na dúvida, um humano escreve.

3. Qual handler usar quando a API da IA está fora do ar?

A) Skip
B) Retry, com Store incomplete executions ligado
C) Rollback
D) Nenhum
B. Falha temporária, nova tentativa.

4. O que o Resume faz no Parse JSON?

A) Apaga o atendimento
B) Usa um valor substituto ("não encontrou") e segue para a rota B
C) Reenvia ao aluno
D) Para o cenário
B. JSON estranho vira trabalho humano.
Recapitulando

Cada caso tem caminho,
cada erro tem destino

O Router separa as respostas encontradas com confiança alta (rota A: sugestão gravada e revisor avisado) de todo o resto (rota B, de fallback: atendimento sem resposta, rascunho novo na FAQ e equipe avisada). Movemos a resposta ao site para antes da IA. Conhecemos os error handlers (Retry, Skip, Resume, Commit e Rollback) e aplicamos Retry na IA e no Gmail e Resume no Parse JSON, com execuções incompletas guardadas. Por fim, sabotamos o cenário de propósito para provar que nenhuma pergunta se perde.
