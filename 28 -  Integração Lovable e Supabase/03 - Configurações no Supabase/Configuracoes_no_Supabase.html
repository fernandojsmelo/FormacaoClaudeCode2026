Passos 1 e 202

Conta e organização

1
Acesse supabase.com e crie a conta. Use o e-mail que você vai querer receber avisos de cobrança e segurança.
2
Ative a autenticação em dois fatores na sua conta. Ela protege todos os projetos que ficarão debaixo dela.
3
Crie uma organização no plano Free. Para o curso, algo como "Minha Estante (curso)".
O que é a organização

É a "pasta" que agrupa projetos, membros da equipe e cobrança. O plano (Free, Pro…) é escolhido para a organização.

Por que isso importa no Lovable

Na aula 04, você vai autorizar o Lovable a acessar uma organização. Uma organização só para o curso deixa claro o que o Lovable pode ver e mexer.

O plano Free tem limite de 2 projetos ativos. Se você já usa o Supabase em outros projetos, confira quantos estão ativos antes de criar mais um.

Região04

Por que São Paulo?

Desempenho

Cada projeto roda numa região principal. Quanto mais perto dos usuários, mais rápido o app responde. Para leitores no Brasil, sa-east-1 é a escolha natural.

Onde os dados ficam

A região também define onde os dados principais são armazenados. Para quem precisa que os dados fiquem numa jurisdição, a documentação recomenda escolher uma região específica, e não um agrupamento geral.

Não é selo de conformidade

A própria documentação avisa: escolher a região é um controle de localização dos dados, não prova de conformidade com leis como a LGPD. Conformidade envolve base legal, transparência e segurança (módulo 26).

O Minha Estante vai guardar nome e e-mail dos leitores, que são dados pessoais. Região no Brasil, RLS em todas as tabelas e dados de teste fictícios são o começo certo.

Passo 506

A URL e as chaves

Project Settings → API Keys · reprodução ilustrativa, com chaves mascaradas
Project URL

O endereço do seu backend, no formato https://…supabase.co. Não é segredo.

Publishable key

sb_publishable_… Pode ir no navegador se o RLS estiver ativo: ela só faz o que as regras permitem.

Secret key

sb_secret_… Só no servidor. Ignora o RLS. Nunca no código do app, no chat ou num print.

Projetos também têm as chaves antigas anon (pública) e service_role (secreta). Os dois sistemas funcionam ao mesmo tempo, e todas as chaves ficam em Settings → API Keys.
Segurança07

E se uma chave vazar?

Vazou a secret key (ou a antiga service_role)? Trate como incidente, na ordem que a documentação recomenda:

1
Sem pressa, corrija a causa do vazamento antes de trocar qualquer coisa.
2
Crie uma nova secret key em Settings → API Keys.
3
Troque a chave antiga pela nova em todos os lugares que a usam e confirme que tudo funciona.
4
Só então aposente a antiga: apague a secret key (irreversível) ou desative as chaves antigas (reversível).
Onde uma chave costuma vazar
  • Colada no chat de uma IA "só para ela ajudar"
  • Em print de tela postado para pedir ajuda
  • Escrita direto no código e enviada ao GitHub
  • Num arquivo .env compartilhado por engano
A publishable key aparecer no navegador é normal. O perigo real é a secret fora do servidor, ou uma tabela sem RLS.

Passo 6 · E-mails09

O e-mail padrão tem limites

Todo projeto vem com um servidor de e-mail para você explorar o Auth. Ele não é para produção, e isso vai aparecer nos testes da aula 06.

As duas restrições
  • Só envia para membros da equipe da organização. Para qualquer outro endereço, a mensagem falha com Email address not authorized
  • Limites de envio baixos, que podem mudar com o tempo
Preparando os testes do curso

Convide os e-mails que você vai usar nos testes como membros da organização (aba Team). Assim a confirmação de cadastro chega.

Para usuários reais

Configure um SMTP próprio nas configurações de Authentication, com um serviço de envio como Resend, Amazon SES, Postmark, SendGrid, ZeptoMail ou Brevo. É o que tira os limites acima.

Não publique um app com login para o público usando o e-mail padrão: cadastros de fora da equipe não recebem a confirmação.

Armadilhas11

Erros comuns na configuração

Colar a secret key no chat do Lovable. A conexão é por autorização. A secret key não entra em nenhum chat.
Senha do banco anotada em lugar nenhum. Use o gerador e salve no gerenciador de senhas no mesmo minuto.
Região escolhida no automático. Longe dos usuários, o app fica mais lento, e trocar depois não é simples.
"O e-mail de confirmação não chega." No servidor padrão, só membros da equipe recebem. Convide o e-mail de teste ou configure SMTP próprio.
Criar tabelas antes do Lovable. O app espera a estrutura que o Lovable cria e registra nas migrations.
Esquecer o limite do Free. 2 projetos ativos e pausa após 1 semana sem uso.
Quiz de fixação12

Teste o que ficou

1. Qual região escolher para um app com leitores no Brasil?

A) East US (North Virginia)
B) South America (São Paulo), sa-east-1
C) Tanto faz
D) A primeira da lista
B. Mais perto dos usuários e com os dados principais no Brasil.

2. Qual chave pode aparecer no navegador?

A) A secret key
B) A publishable key, com RLS ativo
C) A senha do banco
D) Nenhuma
B. Ela só faz o que as regras de RLS permitem. A secret ignora o RLS.

3. O cadastro de teste não recebe o e-mail de confirmação. Causa provável?

A) O Lovable está fora do ar
B) O e-mail padrão só envia para membros da equipe
C) A região errada
D) Falta a secret key
B. Convide o e-mail de teste para a organização ou configure SMTP próprio.

4. A secret key vazou. Qual é o primeiro passo?

A) Apagar a chave imediatamente
B) Corrigir a causa do vazamento
C) Trocar de região
D) Apagar o projeto
B. Depois: criar nova chave, trocar em todos os lugares, e só então aposentar a antiga.
