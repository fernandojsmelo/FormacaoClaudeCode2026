Por que SQLite

O SQLite é um banco de dados num único arquivo, sem servidor para instalar. O Python já traz o módulo sqlite3 na biblioteca padrão: nenhuma dependência nova, o que combina com a rule do projeto ("sem bibliotecas novas sem perguntar").

Para muitos usuários ao mesmo tempo, num servidor, o caminho seria PostgreSQL ou MySQL. Para um app pessoal ou de estudo, o SQLite resolve.
Plan02

Planejar antes de migrar

Mudar onde os dados moram mexe em várias partes do app. É um bom caso para o modo Plan:

Planeje a migração do ToDo List para SQLite: - as tarefas passam a ficar num arquivo tarefas.db, ao lado do app.py; - crie um módulo db.py com as funções de acesso (criar tabela, listar, adicionar, marcar, remover, remover concluídas); - o app.py só chama essas funções; - use o sqlite3 da biblioteca padrão e consultas parametrizadas; - tudo o que funciona hoje continua igual. Mostre o esquema da tabela. Não escreva código.
O que conferir no plano
  • Uma tabela tarefas com id, texto, concluida
  • O id vem do banco (AUTOINCREMENT), não mais do contador da sessão
  • Funções pequenas, uma por operação
  • Consultas com ?, nunca montando SQL com f-string
  • tarefas.db no .gitignore
Banco03

A tabela tarefas

"""Acesso ao banco SQLite das tarefas."""
import sqlite3
from pathlib import Path

CAMINHO_BANCO = Path(__file__).with_name("tarefas.db")


def conectar(caminho=CAMINHO_BANCO):
    conexao = sqlite3.connect(caminho)
    conexao.row_factory = sqlite3.Row
    return conexao


def criar_tabela(conexao):
    conexao.execute(
        """
        CREATE TABLE IF NOT EXISTS tarefas (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            texto TEXT NOT NULL,
            concluida INTEGER NOT NULL DEFAULT 0,
            criada_em TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
        )
        """
    )
    conexao.commit()
ColunaTipoPara quê
idINTEGER PKGerado pelo banco; nunca se repete
textoTEXT NOT NULLO texto da tarefa
concluidaINTEGER 0/1O SQLite não tem booleano; 0 = não, 1 = sim
criada_emTEXTData e hora, preenchida sozinha
CREATE TABLE IF NOT EXISTS cria a tabela só na primeira vez. Rodar de novo não apaga nada.
Banco04

As operações em db.py

def listar(conexao):
    linhas = conexao.execute("SELECT id, texto, concluida FROM tarefas ORDER BY id").fetchall()
    return [{"id": l["id"], "texto": l["texto"], "concluida": bool(l["concluida"])} for l in linhas]


def adicionar(conexao, texto):
    conexao.execute("INSERT INTO tarefas (texto) VALUES (?)", (texto,))
    conexao.commit()


def marcar(conexao, id_tarefa, concluida):
    conexao.execute("UPDATE tarefas SET concluida = ? WHERE id = ?", (int(concluida), id_tarefa))
    conexao.commit()


def remover(conexao, id_tarefa):
    conexao.execute("DELETE FROM tarefas WHERE id = ?", (id_tarefa,))
    conexao.commit()


def remover_concluidas(conexao):
    conexao.execute("DELETE FROM tarefas WHERE concluida = 1")
    conexao.commit()
FunçãoSQL
listarSELECT
adicionarINSERT
marcarUPDATE
remover · remover_concluidasDELETE
Cada escrita termina com commit(): sem ele, a mudança não fica gravada no arquivo.
listar() devolve a mesma lista de dicionários da v2. Por isso o resto do app.py quase não muda.
Segurança05

Consultas parametrizadas

Certo: o valor vai separado, no lugar do ?
conexao.execute("INSERT INTO tarefas (texto) VALUES (?)", (texto,))
Errado: o texto do usuário vira parte do SQL
# NÃO faça assim
conexao.execute(f"INSERT INTO tarefas (texto) VALUES ('{texto}')")
Com a versão errada, uma tarefa como x'); DROP TABLE tarefas;-- poderia mudar o comando. É a injeção de SQL. Uma simples aspa (O'Reilly) já quebraria o INSERT.
Testado no código de referência

A tarefa Ler "O'Reilly"; DROP TABLE tarefas;-- foi salva e lida como texto, com aspas e tudo, e a tabela continuou inteira.

Inclua na rule do projeto: "SQL sempre com parâmetros ?, nunca com f-string". O agente segue a regra em todas as conversas.
App06

O app.py usando o banco

# As tarefas agora ficam no arquivo tarefas.db: sobrevivem a recarregar a página
# e a reiniciar o app.
conexao = db.conectar()
db.criar_tabela(conexao)

with st.form("nova_tarefa", clear_on_submit=True):
    col_texto, col_botao = st.columns([4, 1], vertical_alignment="bottom")
    texto = col_texto.text_input("Nova tarefa", placeholder="O que você precisa fazer?")
    adicionar = col_botao.form_submit_button("Adicionar", width="stretch")

if adicionar:
    texto = texto.strip()
    if not texto:
        st.warning("Digite uma tarefa antes de adicionar.")
    else:
        db.adicionar(conexao, texto)

tarefas = db.listar(conexao)
    if marcada != tarefa["concluida"]:
        db.marcar(conexao, tarefa["id"], marcada)
        st.rerun()
    if col_remover.button("Remover", key=f"remover_{tarefa['id']}"):
        db.remover(conexao, tarefa["id"])
        st.rerun()

if concluidas and st.button("Limpar concluídas"):
    db.remover_concluidas(conexao)
    st.rerun()
  • Sai o st.session_state.tarefas; entra db.listar()
  • Adicionar, marcar, remover e limpar viram chamadas ao db
  • Progresso, filtro e checkboxes continuam iguais à v2
  • As chaves continuam pelo id, agora o id do banco
Separar o acesso a dados em db.py deixa o app.py cuidando só da tela. Se um dia o banco mudar, só o db.py muda.
Versão simples: o app abre uma conexão a cada execução do script. Para apps maiores, peça ao agente para reutilizar a conexão com st.cache_resource ou fechá-la ao fim.

Git10

O banco fica fora do Git

# .gitignore
.venv/
__pycache__/
tarefas.db
  • Código vai para o Git; dados não
  • Cada pessoa que clonar começa com o banco vazio, criado na primeira execução
  • Backup do banco é copiar o arquivo, não commitar
git add app.py db.py .gitignore
git commit -m "ToDo List: salva as tarefas em SQLite"
Se o tarefas.db já entrou num commit, só o .gitignore não basta: rode git rm --cached tarefas.db e faça um commit.
