Host

A aplicação de IA que coordena e gerencia um ou vários clientes MCP.

Cliente

Componente que mantém a conexão com um servidor e busca o contexto que o host vai usar.

Servidor

Programa que oferece contexto aos clientes, rodando local ou remotamente.

Participantes02

Um cliente por servidor

O host cria um cliente MCP para cada servidor, e cada cliente mantém uma conexão dedicada. O exemplo da documentação oficial usa o VS Code; no Cursor é igual:

1
O Cursor (host) conecta ao servidor do GitHub e cria o cliente 1.
2
Conecta ao servidor do Playwright e cria o cliente 2.
3
O agente vê as ferramentas dos dois juntas, mas cada chamada vai pelo cliente certo.
"Local" e "remoto"

Servidor MCP é o programa que serve o contexto, onde quer que rode. Um servidor com stdio roda na mesma máquina e normalmente atende um cliente: é o "servidor local". Um servidor com Streamable HTTP roda numa plataforma e atende muitos clientes: é o "servidor remoto".

Se um servidor cai, os outros continuam funcionando: o Cursor isola as falhas por servidor e marca só aquela chamada como falha.
Camadas03

Duas camadas: dados e transporte

Camada de transporte (externa)

Canais de comunicação e autenticação: abre a conexão, enquadra as mensagens e protege a troca entre os participantes.

Camada de dados (interna)

O protocolo em JSON-RPC 2.0: descoberta de versão e capacidades, as primitivas (tools, resources, prompts) e as notificações.

Camada de dados incluiPara quê
DescobertaVersões, capacidades e identidade do servidor (server/discover)
Recursos do servidorTools, resources e prompts
Recursos do clienteElicitation: o servidor pede algo ao usuário
UtilitáriosNotificações em tempo real e progresso de operações longas
O transporte esconde os detalhes da conexão: a mesma mensagem JSON-RPC vale em qualquer transporte.
Transporte04

stdio e Streamable HTTP

stdio

Usa a entrada e a saída padrão de um processo para falar com processos locais na mesma máquina. Desempenho máximo, sem custo de rede. O Cursor inicia o servidor com o comando do mcp.json e conversa pelo stdin/stdout.

Por isso um servidor stdio deve escrever logs no stderr, nunca no stdout: o stdout é do protocolo.
Streamable HTTP

HTTP POST para as mensagens do cliente ao servidor, com Server-Sent Events opcionais para streaming. Permite servidores remotos e autenticação HTTP padrão: bearer token, chave de API, cabeçalhos. O MCP recomenda OAuth para obter os tokens.

Primitivas05

O que o servidor oferece

PrimitivaO que éMétodosExemplo
ToolsFunções executáveis para a IA agirtools/list · tools/callConsultar o banco, criar uma issue
ResourcesFontes de dados que dão contextoresources/list · resources/readEsquema do banco, conteúdo de um arquivo
PromptsModelos reutilizáveis de interaçãoprompts/list · prompts/getExemplos de uso das ferramentas
O padrão é sempre o mesmo: listar o que existe (*/list) e depois pegar ou executar. Como a lista é consultada na hora, ela pode mudar com o tempo.
O MCP também tem extensões opcionais, como Tasks (operações longas, consultadas depois) e Apps (interface interativa no chat, suportada pelo Cursor).
Primitivas06

E o que o cliente oferece

Elicitation

O servidor pede uma informação a mais ao usuário ou uma confirmação de ação, com o método elicitation/create. O Cursor suporta: a pergunta aparece para você no chat.

O cliente declara em cada requisição o que sabe fazer (por exemplo, "elicitation": {}). Assim o servidor nunca pede algo que o cliente não consegue atender.
Descontinuado em 2026-07-28O que fazer
Sampling (o servidor pede uma resposta ao modelo do cliente)Ainda na especificação, mas com remoção prevista
Logging (o servidor manda logs ao cliente)Logar no stderr (stdio) ou usar OpenTelemetry
Recursos descontinuados ficam na especificação por pelo menos doze meses (ou noventa dias, numa exceção prevista) antes de poderem ser removidos.
Protocolo07

Sem estado: cada requisição se explica

Na versão atual, o MCP é um protocolo sem estado: toda requisição leva no campo _meta a versão do protocolo, as capacidades do cliente e, normalmente, a identidade do cliente. O servidor processa cada uma sozinha, sem depender de conexão anterior.

  • Todo servidor implementa server/discover: devolve versões aceitas, capacidades e identidade
  • Chamar o server/discover é opcional para o cliente; é o jeito prático de saber tudo numa requisição só
  • Se a versão não for aceita, o servidor responde com UnsupportedProtocolVersionError e a lista de versões; o cliente tenta de novo
Resposta do server/discover (resumida)
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "tools": { "listChanged": true },
      "resources": {}
    },
    "_meta": {
      "io.modelcontextprotocol/serverInfo":
        { "name": "example-server", "version": "1.0.0" }
    }
  }
}
Mensagens08

Descobrindo as ferramentas

Requisição · tools/list
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo":
        { "name": "example-client", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities":
        { "elicitation": {} }
    }
  }
}
Resposta (uma das ferramentas)
{
  "jsonrpc": "2.0", "id": 2,
  "result": { "tools": [ {
    "name": "weather_current",
    "title": "Weather Information",
    "description": "Get current weather information
                    for any location worldwide",
    "inputSchema": {
      "type": "object",
      "properties": {
        "location": { "type": "string" },
        "units": { "type": "string" } },
      "required": ["location"] }
  } ] }
}
O nome, a descrição e o inputSchema (JSON Schema dos argumentos) são o que o modelo lê para decidir quando e como usar a ferramenta. É isso que ocupa a categoria "MCP" do contexto.
Mensagens09

Chamando uma ferramenta

Requisição · tools/call
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "weather_current",
    "arguments": {
      "location": "San Francisco",
      "units": "imperial"
    },
    "_meta": { … versão, cliente, capacidades … }
  }
}
Resposta
{
  "jsonrpc": "2.0", "id": 3,
  "result": {
    "resultType": "complete",
    "content": [ {
      "type": "text",
      "text": "Current weather in San Francisco:
               68°F, partly cloudy…"
    } ]
  }
}
O content é uma lista com type: texto, imagem (em base64) e outros tipos. É assim que um servidor de navegador devolve um screenshot.
Fluxo completo10

Do pedido à resposta

1 · PedidoVocê pede ao agente: "liste as issues abertas"
2 · DecisãoO modelo escolhe uma tool MCP e os argumentos
3 · RoteamentoO host acha o cliente do servidor dessa tool e pede aprovação
4 · ExecuçãoO cliente envia tools/call; o servidor executa
5 · ResultadoO conteúdo volta para o modelo, que continua a tarefa
Pseudocódigo da documentação oficial
# Pseudo-código: como a aplicação de IA executa uma chamada de ferramenta
async def handle_tool_call(conversation, tool_name, arguments):
    client = app.find_mcp_client_for_tool(tool_name)
    result = await client.call_tool(tool_name, arguments)
    conversation.add_tool_result(result.content)
No Cursor, você vê os passos 3 a 5 no chat: o pedido de aprovação, os argumentos (seta ao lado do nome da ferramenta) e a resposta, que dá para expandir.
Atualizações11

Notificações em tempo real

1
O servidor anuncia em capabilities que avisa mudanças: "tools": {"listChanged": true}.
2
O cliente abre um canal com subscriptions/listen, pedindo "toolsListChanged": true.
3
O servidor confirma com notifications/subscriptions/acknowledged.
4
Quando as ferramentas mudam, chega notifications/tools/list_changed, e o cliente pede o tools/list de novo.
Notificação
{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/subscriptionId": 4
    }
  }
}
  • Sem id: notificação não tem resposta (regra do JSON-RPC 2.0)
  • Opcional: só chega para quem pediu
  • Melhor esforço: pode se perder numa reconexão; o cliente também deve consultar de tempos em tempos
Versões12

Como o protocolo evolui

As versões do MCP são datas no formato AAAA-MM-DD: a data da última mudança incompatível. Mudanças compatíveis não trocam a versão.

EstadoSignificado
DraftEm andamento, ainda não pronta para uso
CurrentA versão atual, pronta para uso; pode receber mudanças compatíveis
FinalVersões passadas e completas, que não mudam mais
Versão atual

A versão current em outubro de 2026 é a 2026-07-28, a dos exemplos desta aula. Ela trouxe o modelo sem estado com server/discover e descontinuou sampling e logging.
