Visão01

Os fluxos de uma conta

1
Criar conta

Nome, e-mail e senha. O Supabase cria o usuário.

2
Confirmar e-mail

Link enviado por e-mail. Sem confirmar, não entra.

3
Entrar

E-mail e senha. A sessão fica guardada no navegador.

4
Esqueci a senha

Link por e-mail para uma página de nova senha.

5
Sair

Encerra a sessão; a estante volta a pedir login.

Onde isso é configurado

Com Supabase próprio, as configurações de login ficam no painel do Supabase (Authentication), e não nas telas do Lovable. O Lovable constrói as páginas e a lógica; o Supabase guarda usuários, senhas e sessões.

Assim que existir um leitor logado, as políticas da tabela livros (aula 05) passam a valer: cada um só verá os próprios livros.
Antes do prompt02

Três ajustes no painel do Supabase

1 · Site URL e Redirect URLs

Em Authentication → URL Configuration. O Site URL vem como localhost:3000: sem trocar, o link de confirmação leva a um endereço que não existe.

  • Site URL: o endereço do preview do projeto no Lovable (depois, o publicado)
  • Redirect URLs: o preview e o publicado
2 · Confirmação de e-mail

Em projetos hospedados, exigir a confirmação vem ligado por padrão (página de provedores do Auth). Deixe ligado: garante que o e-mail é mesmo do leitor.

Lembre da aula 03: o e-mail padrão só envia para membros da equipe. Teste com um e-mail convidado.

3 · Regras de senha

A documentação recomenda mínimo de 8 caracteres e exigir tipos variados (letras, números, símbolos).

A proteção contra senhas vazadas (base HaveIBeenPwned) existe do plano Pro do Supabase em diante.

O endereço exato do preview aparece no Lovable. Copie de lá, cole no Supabase e confira se não sobrou espaço ou barra no fim.
Banco de dados03

A tabela perfis

Os usuários ficam no esquema auth do Supabase, que não é exposto na API por segurança. Para mostrar o nome do leitor no app, a documentação recomenda uma tabela própria no esquema public, ligada ao usuário.

ColunaRegra
idMesmo id do usuário; aponta para auth.users com on delete cascade: apagou o usuário, some o perfil
nome_exibicao"Como quer ser chamado", obrigatório
criado_emPreenchido automaticamente
RLS de perfis

O leitor lê e altera só o próprio perfil. Nada de leitura pública por enquanto.

Criado sozinho no cadastro

Um gatilho (trigger) cria o perfil sempre que um usuário novo é cadastrado, com o nome informado no formulário.

Cuidado: se o gatilho falhar, o cadastro inteiro falha, e ninguém consegue criar conta. A própria documentação pede para testar bem. Faça um cadastro de teste logo depois de aprovar a migration.
Plan mode04

O prompt do login

Prompt (Plan mode): Adicione login por e-mail e senha usando o Supabase Auth do projeto (veja o Knowledge): 1. Página /entrar com abas "Entrar" e "Criar conta". Criar conta pede nome, e-mail e senha (mínimo 8 caracteres). 2. Após criar conta, tela "Confira seu e-mail" com opção de reenviar. 3. "Esqueci minha senha": envia o link e uma página /nova-senha para definir outra. 4. Tabela "perfis" (id ligado ao usuário, on delete cascade; nome_exibicao) criada por trigger no cadastro. RLS: cada um lê e altera só o próprio perfil. 5. Cabeçalho: logado, mostra o nome e um menu com "Meu perfil" e "Sair". 6. /estante exige login; logado, mostra "Olá, [nome]" e o estado vazio. Mensagens de erro em português.
No plano, confira
  • Usa o Supabase Auth do projeto conectado (nada de Cloud)
  • Migration de perfis com RLS e o gatilho
  • Os links de e-mail voltam para páginas do app
  • /estante protegida no app e no banco (RLS)
Serão pelo menos duas aprovações: a migration de perfis (com o gatilho) e as mudanças de código. Leia a migration como na aula 04.

Recuperação07

Esqueci minha senha

1
Em /entrar, o leitor clica em Esqueci minha senha e informa o e-mail.
2
O Supabase envia um link que aponta para /nova-senha do app. Esse endereço precisa estar nas Redirect URLs.
3
Na página, o leitor define a nova senha, com as mesmas regras do cadastro.
4
O app confirma e leva para a estante.
Mensagem neutra

Depois de pedir o link, mostre sempre "Se houver uma conta com esse e-mail, enviamos um link". Dizer "e-mail não cadastrado" revela quem usa o app.

Prompt, se precisar: Na tela de "Esqueci minha senha", mostre sempre a mesma mensagem, exista ou não a conta: "Se houver uma conta com esse e-mail, enviamos um link para criar uma nova senha."

Teste de segurança09

Dois leitores, duas estantes

Login funcionando não prova que um leitor não vê o outro. Crie dois leitores de teste (dois e-mails de membros da equipe) e confira.

1
Cadastre a Leitora A numa janela e o Leitor B numa janela anônima.
2
No painel do Supabase, em Authentication → Users, os dois aparecem confirmados.
3
No Table Editor, perfis tem duas linhas, cada uma com seu nome: o gatilho funcionou.
4
Cada janela mostra só o próprio nome. Sem login, /estante pede para entrar.
Prompt (Chat mode) · conferência: Liste as políticas RLS das tabelas perfis e livros. Um leitor logado consegue ler o perfil ou os livros de outro leitor? Não altere nada.

Armadilhas10

Erros comuns com login

Desligar a confirmação de e-mail "para facilitar". Qualquer um cria conta com o e-mail de outra pessoa. Teste com membros da equipe em vez disso.
Proteger só a tela. Esconder a /estante sem login não protege dados. Quem protege é o RLS; a tela é só conforto.
Site URL em localhost. Todo link de e-mail leva a um endereço que não existe. Troque antes do primeiro cadastro.
Gatilho sem teste. Se ele falhar, ninguém consegue se cadastrar. Teste logo após aprovar.
"E-mail não cadastrado". Na recuperação de senha, mensagem neutra: não revele quem usa o app.
Testar com um leitor só. Vazamento entre contas só aparece com duas.
Quiz de fixação11

Teste o que ficou

1. O link de confirmação abre localhost:3000. O que ajustar?

A) A senha do banco
B) Site URL e Redirect URLs no Supabase
C) O Knowledge
D) A região
B. Em Authentication → URL Configuration, com o endereço do app.

2. Por que criar a tabela perfis no esquema public?

A) O esquema auth não é exposto na API
B) É mais bonito
C) O Lovable exige
D) Para pular o RLS
A. A tabela própria, com RLS, é o jeito seguro de ler dados do usuário.

3. O que acontece se o gatilho de perfis falhar?

A) Nada
B) O perfil fica sem nome
C) O cadastro inteiro falha
D) O app sai do ar
C. Por isso se testa um cadastro logo após aprovar.

4. Como provar que um leitor não vê o outro?

A) Com um leitor só
B) Com dois leitores e a conferência das políticas RLS
C) Olhando o código
D) Não precisa
B. Duas janelas, duas contas e as políticas explicadas no Chat mode.
