Conceito01

Por que um projeto separado?

Daria para enfiar uma "área da equipe" dentro do site. Mas o site é público e o painel é interno: públicos, riscos e ritmo de mudança diferentes. Separar deixa cada um mais simples e evita que um ajuste no site quebre a rotina da equipe (e vice-versa).

Site da Café SamambaiaPainel Samambaia
Quem usaQualquer pessoa na internetSó a equipe do café, com login
ObjetivoEncantar e converter em visita/reservaOperar o dia: ver, confirmar, cancelar
VisualFotos, clima, marca em destaqueDenso, legível, rápido de ler no balcão
RiscoFormulário aberto a qualquer umDados pessoais de clientes (nome, WhatsApp)
PublicaçãoDomínio público, SEO importaAcesso restrito, SEO não importa
Ponto técnico importante: segundo o FAQ oficial do Lovable, dois projetos não compartilham o mesmo banco do Lovable Cloud. Cada projeto tem o seu. Por isso o painel terá a própria tabela, e na aula 08 o site passará a enviar cada reserva para ele. (Quem precisa de um banco comum usa um Supabase externo conectado aos dois projetos, fora do escopo deste módulo.)

Briefing03

Quatro perguntas antes do primeiro prompt

Na aula 04 o briefing do site partiu do cliente final. Aqui o "cliente" é a equipe. Responda por escrito. Essas respostas viram o prompt e o Knowledge do projeto.

1
Quem usa? Gerente e atendentes, no computador do balcão e às vezes no celular.
2
O que precisa fazer? Ver as reservas do dia e, a partir da aula 08, confirmar ou cancelar.
3
Quais dados? Data, horário, nome, nº de pessoas, WhatsApp, observação e status.
4
O que não pode acontecer? Alguém de fora se cadastrar ou ler os dados dos clientes.
Knowledge do projeto (Settings → Knowledge)
Knowledge: Painel Samambaia é uma ferramenta INTERNA da equipe da Café Samambaia (cafeteria em SP). - Idioma: português do Brasil; datas dd/mm, 24h. - Visual: mesma marca do site (verde #2F5D50, creme #F4EDE1, terracota #9A5A34), porém mais denso e legível: tabelas, números grandes. - Todo acesso exige login. Não existe cadastro público: novos membros entram por convite. - Dados de clientes são pessoais (LGPD): mostrar só o necessário e nunca em páginas públicas.
Plan mode04

Primeiro o plano, depois o código

Um projeto com login e banco mexe em várias camadas ao mesmo tempo. Use o Plan mode (Alt+P alterna os modos): o Lovable propõe o plano, você revisa, e só então ele constrói. O plano fica salvo em .lovable/plan.md.

Prompt (Plan mode): Crie o Painel Samambaia, ferramenta interna da equipe (veja o Knowledge). 1. Login por e-mail e senha usando o Lovable Cloud. Sem tela de cadastro. 2. Tabela "reservas": data, horario, nome, pessoas, whatsapp, observacao, status (pendente | confirmada | cancelada) e criado_em. 3. Só usuários logados podem ler a tabela. Ninguém anônimo lê ou grava. 4. Página "Reservas de hoje": 4 indicadores e a lista ordenada por horário, somente leitura. 5. Menu lateral com Reservas, Dashboard e Equipe (os dois últimos como "em breve"). 6. Popule 9 reservas FICTÍCIAS para hoje.
Plano proposto ilustrativo
Plano · Painel Samambaia 1. Autenticação Página /login (e-mail + senha); rotas protegidas redirecionam para /login. 2. Banco (Lovable Cloud) Tabela reservas + tipo de status. Políticas RLS: SELECT só para usuários autenticados. 3. Interface Layout com menu lateral; página /reservas com indicadores e tabela. 4. Dados de exemplo 9 reservas fictícias na data de hoje. # Perguntas: o cadastro fica desativado # no painel do Cloud? (recomendado: sim)
Uma mensagem no Plan mode custa 1 crédito (mais o que subagentes consumirem). Revise o plano com calma: corrigir antes de construir sai mais barato do que desfazer depois.
Autenticação05

Login da equipe, sem cadastro aberto

Tela de login · reprodução ilustrativa

Tirar o botão "Criar conta" da tela não basta: quem conhece o endereço do serviço ainda poderia tentar se cadastrar. O cadastro precisa ser fechado na configuração.

1
Abra Cloud → Users e, nas configurações de autenticação, desative o cadastro (sign-up).
2
Em Add user, escolha Send invitation: a pessoa recebe um e-mail e define a própria senha.
3
Create new user também existe, mas aí você define a senha e precisa repassá-la. Prefira o convite.
Uma conta por pessoa, nunca um login compartilhado "equipe@". Quando alguém sai da equipe, você remove só aquela conta.

A tabela reservas

É a mesma informação do formulário do site, mais o que a equipe precisa para operar. Confira a estrutura em Cloud → Database depois que o Lovable criar.

Regras no próprio banco
  • pessoas de 1 a 6
  • status só aceita os três valores
  • nome, data, horario e whatsapp obrigatórios

Validar no formulário melhora a experiência; validar no banco garante a regra mesmo se alguém contornar a tela.

Segurança07

Quem pode ver o quê: RLS

O Lovable Cloud é construído sobre o Supabase, que protege tabelas com Row Level Security (RLS): regras no banco dizendo quem pode ler, inserir, alterar ou apagar. A tela esconder um dado não é proteção. A regra no banco é.

OperaçãoAnônimoEquipe logadaQuando
Ler (SELECT)✗✓Aula 07
Alterar status (UPDATE)✗✓Aula 08
Criar (INSERT)✗via funçãoAula 08
Apagar (DELETE)✗✗Nunca: usa-se "cancelada"
Prompt (Chat mode) · conferência: Liste as políticas RLS da tabela reservas e explique em linguagem simples o que um visitante anônimo consegue fazer com ela. Não altere nada.
Teste de verdade

Abra o painel publicado numa aba anônima, sem login. Deve cair na tela de login e nenhuma reserva pode aparecer.

Security scan

No menu More → Security, rode o Quick scan. Tabela sem RLS ou com política aberta demais aparece como alerta.

Armadilhas11

Erros comuns neste tipo de projeto

"Use o mesmo banco do site." Com Lovable Cloud isso não existe: cada projeto tem o seu. O Lovable pode tentar improvisar. Planeje a ponte (aula 08) ou um Supabase externo.
Esconder em vez de proteger. Tirar o botão de cadastro ou ocultar a lista sem login não impede ninguém. A proteção é o cadastro desativado + RLS.
Login compartilhado. Uma senha para toda a equipe impede saber quem fez o quê e obriga a trocar a senha de todos quando alguém sai.
Dados reais em teste. Copiar reservas verdadeiras "só para ver como fica" coloca dados pessoais num ambiente de testes. Use sempre dados fictícios.
Querer tudo num prompt só. Login, banco, RLS, tela e integração de uma vez geram um plano enorme e difícil de revisar. Vá em camadas.
Pular o Plan mode. Em projeto com banco, uma decisão errada de estrutura custa várias mensagens para desfazer.
Quiz de fixação12

Teste o que ficou

1. Por que o painel tem a própria tabela de reservas, em vez de ler a do site?

A) É mais rápido
B) Dois projetos não compartilham o banco do Lovable Cloud
C) O site não tem banco
D) Por causa do SEO
B. Cada projeto tem o próprio Cloud. Na aula 08 o site envia as reservas para o painel.

2. Qual combinação realmente impede estranhos de entrar?

A) Esconder o botão "Criar conta"
B) Cadastro desativado + convite por e-mail
C) Uma senha forte compartilhada
D) Não divulgar o endereço
B. A configuração fecha a porta; o convite dá uma chave a cada pessoa.

3. O que é RLS?

A) Um tema visual
B) Regras no banco sobre quem lê e altera cada linha
C) Um tipo de login
D) Um relatório de uso
B. Row Level Security: a proteção fica no banco, não na tela.

4. Por que apagar (DELETE) fica proibido para a equipe?

A) Custa crédito
B) O banco não permite
C) Cancelar preserva o histórico para o dashboard da aula 09
D) Por causa do celular
C. Reserva cancelada vira dado útil (taxa de cancelamento); apagada, some.
