Visão geral01

Quem pensa e o que ele sabe

Model · quem pensa

O modelo de linguagem que lê o pedido, decide os passos e escreve o código. Muda a qualidade, a velocidade e o custo de cada pedido. Dá para trocar a qualquer momento.

Rules · o que ele sabe

Modelos não guardam memória entre conversas. As rules são instruções permanentes, incluídas no início do contexto, para o agente seguir seu estilo, seus padrões e seus fluxos sem você repetir.

Models02

Dois bolsos de uso

Nos planos Pro, Pro+ e Ultra, o uso incluído é dividido em dois bolsos, cada um renovado no ciclo mensal. O modelo escolhido decide de qual bolso sai e com que rapidez ele acaba.

Cursor Models

Composer 2.5 e a família Grok 4.5, 4.6 e 4.7 (treinada pelo Cursor com a SpaceXAI). Têm bem mais uso incluído. Também é o único bolso do plano Start (Índia).

Other Models

Modelos de terceiros (Anthropic, OpenAI, Google, Meta e outros), cobrados ao preço da API de cada um. Ao esgotar, dá para seguir com uso sob demanda, aos mesmos preços.

Os dois bolsos aparecem nas configurações do editor e no painel cursor.com/dashboard/usage.
Nos planos Teams e Enterprise, pedidos a modelos de terceiros têm ainda a taxa do Cursor: US$ 0,25 por milhão de tokens. Os modelos próprios do Cursor ficam isentos.
Models03

Os modelos do Cursor

Composer 2.5
  • Modelo próprio do Cursor, ajustado para usar ferramentas, editar arquivos e operar o terminal dentro do Cursor.
  • Forte em tarefas longas de agente; melhor calibragem de esforço e entendimento da intenção que o Composer 2.
  • A variante Fast é a padrão no produto (mesma inteligência, mais rápida).
  • Preço: US$ 0,50 entrada / US$ 2,50 saída por milhão de tokens; Fast: US$ 3 / US$ 15.
Grok 4.7
  • Modelo de ponta do Cursor com a SpaceXAI, para o trabalho mais difícil e demorado. Confere melhor os próprios resultados que o 4.6.
  • Contexto de 256 mil tokens, ou 500 mil no modo de contexto longo (cobrado em dobro).
  • Quatro níveis de esforço: xhigh, high (padrão), medium e low.
  • Preço: US$ 2 / US$ 6; Fast (padrão no Pro e acima): US$ 4 / US$ 12.
A própria ajuda do Cursor resume: Grok 4.7 é o carro-chefe para as tarefas mais difíceis e longas; Composer é o modelo rápido e econômico, capaz na maioria das tarefas e feito para programar de forma interativa.

Models06

Auto e o Cursor Router

Com Auto, você não escolhe o modelo: o Cursor escolhe a cada pedido, equilibrando inteligência, custo e confiabilidade. É o recomendado para o dia a dia.

Cursor Router (Teams e Enterprise)

Nesses planos, o Auto usa um roteador: um classificador manda os pedidos simples para modelos rápidos e os complexos para os mais capazes. Você escolhe a otimização no seletor:

  • Cost: economiza tokens.
  • Balance: equilibra inteligência, velocidade e custo.
  • Intelligence: os mais capazes para tarefas difíceis.
  • Todo modo do Auto é cobrado ao preço do modelo escolhido pelo roteador
  • Balance e Intelligence gastam o limite mais rápido que Cost
  • Por padrão, o nome do modelo usado fica oculto, para você julgar o resultado e não a marca (o admin pode mostrar)
  • O admin pode impor o Auto: Soft (padrão em conversa nova) ou Hard (trava o seletor)
O plano Start (Índia) não inclui o Auto.
Models07

Esforço, Fast e contexto

Esforço

Vários modelos aceitam níveis de esforço: mais esforço = mais tempo pensando, mais tokens, melhor resultado em problemas difíceis. Ex.: Grok 4.7 (low a xhigh), Gemini 3.8 Flash (low, medium, high), Muse Spark (minimal a max).

Fast

Variante mais rápida do mesmo modelo, geralmente com preço maior (no Grok 4.7, o dobro). No Composer 2.5 e no Grok 4.7 (Pro e acima), o Fast já é o padrão.

Contexto

Quanto o modelo consegue "ver" de uma vez. Vários chegam a 1 milhão de tokens; alguns cobram mais acima de um limite (ex.: Gemini 3.1 Pro acima de 200 mil; Grok 4.7 acima de 256 mil).

Regra prática: comece no esforço padrão. Suba só quando o resultado não vier bom; desça para tarefas simples e repetitivas.
Max Mode existe só nos planos antigos, cobrados por pedido: amplia o contexto, a preço de API + 20%. Nos planos atuais, você não precisa dele.

Rules10

Quatro tipos de rules

TipoOnde ficaVale para
Project Rules.cursor/rules/*.mdc, versionadas no GitAquele projeto, para toda a equipe
User RulesCustomize › Rules; sincronizam com a sua contaTodos os seus projetos, em qualquer computador
Team RulesPainel da equipe (Teams e Enterprise)Todos os projetos da organização; podem ser obrigatórias
AGENTS.mdArquivo Markdown na raiz (e em subpastas)Aquele projeto, do jeito mais simples
Precedência: Team Rules → Project Rules → User Rules. Todas são somadas; se houver conflito, vale a que vem antes.
Alcance: as rules valem para o Agent em todos os modos. Não afetam o Tab, e as User Rules não valem na edição inline (Ctrl + K).
Rules11

Anatomia de uma project rule

Cada rule é um arquivo .mdc em .cursor/rules/: um cabeçalho (frontmatter) e as instruções em Markdown. Um .md comum nessa pasta é ignorado.

Tipo (no menu)CabeçalhoQuando entra
Always ApplyalwaysApply: trueEm toda conversa
Apply to Specific Filesglobs: ...Quando um arquivo que casa está no contexto
Apply Intelligentlydescription: ...O agente lê a descrição e decide
Apply Manuallynenhum dos trêsSó com @nome-da-rule
# .cursor/rules/componentes.mdc --- globs: src/components/**/*.tsx alwaysApply: false --- - Use exports nomeados, não default - Estilos num arquivo .module.css ao lado - Componentes com menos de 200 linhas - Prefira composição a repassar props por várias camadas
Rule "Apply Intelligently" sem description ou "Apply to Specific Files" com padrão que não casa: são as causas mais comuns de "minha rule não funciona".
Rules12

Padrões de arquivo (globs)

PadrãoCasa com
*.tsArquivos .ts na raiz
**/*.tsArquivos .ts em qualquer pasta
src/**Tudo dentro de src/
src/**/*.tsxTodo .tsx dentro de src/
docs/**/*.md, docs/**/*.mdxMarkdown em docs/ (vírgula separa padrões)
tailwind.config.*tailwind.config com qualquer extensão
  • * casa com um trecho do nome; ** atravessa pastas.
  • Separe vários padrões com vírgula.
  • Dentro da rule, use @arquivo.ts para apontar um exemplo em vez de copiar o código: a rule fica curta e não desatualiza.
Rules por arquivo economizam contexto: só entram quando aquele tipo de arquivo está em jogo, ao contrário das "Always Apply".
Rules13

Três jeitos de criar uma rule

Pedindo ao agente

Digite /create-rule e descreva o que quer. O agente cria o arquivo com o cabeçalho certo em .cursor/rules. Também dá para pedir em texto livre.

Pelo Customize

Barra lateral › Customize › Rules › Add Rule. Ali você também vê todas as rules e se estão ativas.

Pela paleta

Ctrl + Shift + P › New Cursor Rule, dê um nome (ex.: react-patterns), escreva e escolha o tipo no menu.

User Rule de exemplo
Responda sempre em português do Brasil, de forma concisa. Mantenha nomes de código e comandos no original. Antes de mudar algo grande, mostre o plano.
Viu o agente errar a mesma coisa duas vezes? É hora de uma rule. No GitHub, dá até para marcar @cursor numa issue ou PR para o agente atualizar a rule.
Rules14

AGENTS.md: o jeito simples

Um arquivo Markdown comum, sem cabeçalho, na raiz do projeto. O Cursor lê automaticamente. É um formato reconhecido por vários agentes, então serve também fora do Cursor.

# AGENTS.md # Instruções do projeto - Use TypeScript em todo arquivo novo - Acesso a dados sempre pelo padrão repository - Componentes com menos de 200 linhas - Rode `npm test` antes de dar a tarefa por concluída
AGENTS.md aninhado

Coloque outros AGENTS.md em subpastas. Eles valem quando o agente trabalha naqueles arquivos, somados aos das pastas acima; o mais específico tem prioridade.

projeto/ AGENTS.md # geral frontend/AGENTS.md # só frontend backend/AGENTS.md # só backend
Precisa escolher quando cada instrução entra (por arquivo, por descrição, manual)? Use as rules .mdc.
Rules15

Rules que funcionam

Faça
  • Menos de 500 linhas por rule; divida as grandes em várias pequenas
  • Uma pasta .cursor/rules simples, um assunto por arquivo, nomes claros
  • Exemplos concretos ou referência a arquivos (@arquivo)
  • Escreva como documentação interna: direto e acionável
  • Comece pequeno e acrescente quando o agente repetir um erro
  • Versione no Git para a equipe aproveitar
Evite
  • Copiar guias de estilo inteiros: use um linter
  • Explicar comandos que o agente já conhece (npm, git, pytest)
  • Regras para casos raros
  • Duplicar código que já existe no projeto: aponte o exemplo
  • Usar rules como único controle de segurança
Para levar rules de um repositório para outro, o Cursor não importa rules soltas: empacote-as num plugin e publique num marketplace.
