A fronteira fundamental

"O quê / por quê" ≠ "como"

Este é o erro mais comum de quem começa: escrever uma spec que já é uma implementação disfarçada. Quando a spec decide o "como", ela rouba do agente exatamente o trabalho que ele faz bem.

Pertence à spec — "o quê / por quê"

  • O comportamento observável do sistema
  • Quem usa e para resolver qual problema
  • As regras de negócio
  • O que caracteriza sucesso e erro
  • Limites que não podem ser violados
│

Não pertence — "como"

  • Nomes de classes, funções e variáveis
  • Estrutura de pastas do projeto
  • Qual algoritmo de ordenação usar
  • Se é for ou map
  • Detalhes internos que ninguém observa de fora
⚠️

A exceção que confirma a regra: às vezes o "como" é requisito. "Tem que ser PostgreSQL porque o time já opera Postgres" não é implementação — é restrição técnica, e tem seção própria na spec. A diferença: você consegue explicar por quê.

Teste rápido: se a resposta para "por que assim?" for "porque o negócio exige", é spec. Se for "porque eu gosto", é código — deixe o agente decidir.

Anatomia

As seis peças de uma spec

Clique em cada peça para ver o que ela contém e como escrevê-la.

Qual problema real isto resolve, e para quem. É a peça que impede que o incremento vire uma solução sem dono.

objetivo
✓ "Permitir que o usuário veja quanto gastou no mês, para decidir se pode fazer uma compra grande." ✗ "Criar endpoint de resumo." // isso é o "como", não o "por quê"

Comportamentos observáveis, em frases que descrevem uma ação e seu resultado. Um requisito por linha; se precisar de "e", provavelmente são dois.

  • O usuário pode registrar uma transação com data, descrição, valor e tipo.
  • O sistema lista todas as transações em ordem decrescente de data.
  • O sistema rejeita transações com valor menor ou igual a zero.

Qualidades transversais: desempenho, segurança, persistência, limites, acessibilidade, custo. São os que mais somem das specs — e os que mais causam retrabalho quando somem.

⚡

Desempenho

"A listagem responde em menos de 300 ms com 10 mil registros."

🔒

Segurança

"A chave da API vem de variável de ambiente, nunca do código."

💾

Persistência

"Os dados sobrevivem a um reinício do servidor."

A peça mais importante da spec inteira. Um critério de aceite é uma afirmação que alguém consegue testar e responder sim ou não, sem opinar. Se dois revisores podem discordar sobre se o critério foi atendido, ele ainda não é um critério.

critérios de aceite
✓ POST /transacoes com valor 0 retorna 422 ✓ GET /transacoes lista as transações criadas ✓ os dados continuam lá depois de reiniciar o servidor ✗ a API deve ser rápida // rápida quanto? ✗ o código deve ser limpo // limpo segundo quem? ✗ tratar os erros direito // quais erros? qual resposta?

O escopo delimita o incremento. O fora-de-escopo é o que impede o agente (e o time) de resolver criativamente um problema que não era para ser resolvido agora.

🧲

O fora-de-escopo é a peça mais subestimada da spec. Sem ela, todo incremento tende a crescer — o agente vê uma lacuna adjacente e a preenche por conta própria.

Decisões de "como" que já foram tomadas e não estão em discussão: stack, versões, bibliotecas obrigatórias, padrões do time, compatibilidade. Escreva também o motivo — sem ele, uma restrição vira mistério para quem lê depois.

  • Python 3.11+ com FastAPI — é o padrão do restante do sistema.
  • SQLite — o app precisa rodar sem serviço externo na máquina do aluno.

Lado a lado

Spec vaga × spec precisa

A mesma funcionalidade, escrita de dois jeitos. Alterne entre as abas e repare em quantas perguntas a primeira versão deixa em aberto.

spec vaga
Funcionalidade Filtro de transações. Descrição O usuário precisa conseguir filtrar suas transações de forma prática. Deve funcionar bem e ser rápido. Tratar os erros adequadamente.

Parece razoável — e é exatamente esse o perigo. É um texto que soa como especificação, mas não permite verificar nada. "Prática", "bem", "rápido" e "adequadamente" são quatro decisões terceirizadas.

spec precisa
Objetivo Permitir que o usuário encontre transações específicas sem percorrer a lista inteira. Requisitos funcionais · filtrar por categoria (valor exato) · filtrar por período (data inicial e final, inclusivas) · filtrar por faixa de valor (mínimo e máximo) · os filtros são combináveis entre si (E lógico) Requisitos não-funcionais · resposta abaixo de 300ms com 10.000 transações Fora de escopo · busca por texto livre na descrição · filtros salvos pelo usuário Critérios de aceite ✓ GET /transacoes?categoria=alimentacao devolve só essa categoria ✓ categoria inexistente devolve lista vazia e 200 (não é erro) ✓ data inicial maior que a final devolve 422 com mensagem clara ✓ os três filtros combinados devolvem a interseção correta ✓ sem nenhum filtro, devolve tudo (comportamento atual preservado)
Na versão vaga……a pergunta escondidaNa versão precisa
"filtrar"por quais campos?categoria, período e faixa de valor
"de forma prática"combináveis ou um de cada vez?combináveis, com E lógico
"rápido"quanto? com qual volume?< 300 ms com 10 mil registros
"tratar os erros"categoria inexistente é erro ou lista vazia?lista vazia com 200 — decisão explícita
(ausente)busca textual entra?fora de escopo, declarado
🎯

Repare: a spec precisa não ficou longa por enfeite. Cada linha a mais fecha uma pergunta que alguém teria que responder no chute.

O teste definitivo

A regra de ouro

Se uma pessoa nova no time conseguisse implementar a funcionalidade lendo apenas a spec — sem perguntar nada a ninguém — então o agente também consegue.

É um teste prático, não filosófico. Leia sua spec fingindo que você acabou de chegar ao projeto e que não pode perguntar nada. Toda vez que você pensar "hmm, aqui eu perguntaria…", achou um buraco.
