O problema

"Codar no chute"

Você abre o terminal, descreve o que quer em uma frase e espera o melhor. Às vezes funciona. O problema não é a falha — é a imprevisibilidade.

claude — pedido sem contexto
> faz um sistema de login pra mim // o agente agora precisa adivinhar: // · e-mail e senha? OAuth? magic link? // · onde persiste? já existe banco? // · sessão por cookie ou JWT? // · precisa de "esqueci minha senha"? // · qual o critério para dizer que está pronto? ✗ 400 linhas depois: "não era bem isso"

Cada decisão que você não tomou, alguém tomou por você — e você só descobre qual foi depois que o código está escrito. Revisar vira arqueologia: em vez de comparar o resultado com um alvo, você tenta reconstruir qual alvo o agente imaginou.

🎲

Imprevisível

O mesmo pedido, feito duas vezes, produz dois sistemas diferentes.

🔍

Difícil de revisar

Sem alvo declarado, não existe "certo" ou "errado" — só gosto pessoal.

🔁

Retrabalho caro

A correção chega quando o código já existe, que é o momento mais caro possível.

A virada de chave

A spec é a fonte da verdade

SDD inverte a hierarquia entre spec e código. A especificação deixa de ser um subproduto e passa a ser o artefato principal; o código é o que se deriva dela.

Modelo antigo

código → (talvez) doc

  • O código é a única verdade
  • A doc é escrita depois, se sobrar tempo
  • Divergiu? A doc está errada
  • A intenção fica só na cabeça de quem escreveu
▶

Modelo SDD

spec → plano → código

  • A spec é a única verdade
  • O código é um artefato derivado dela
  • Divergiu? Ou o código está errado, ou a spec mudou — e isso é decidido, não descoberto
  • A intenção fica registrada e revisável
Se o código é o "como", a spec é o "o quê" e o "por quê". Trocar de linguagem muda o "como" inteiro — e não deveria mudar uma linha do "o quê".
🧭

Este é o fio condutor de todo o curso: nos dois projetos práticos você vai construir apps diferentes, em Python e em JavaScript, com o mesmo ciclo. A prova de que a spec é a verdade é ela sobreviver à troca de stack.

Mudança de era

Da documentação morta à spec executável

Todo dev já viu um README que descreve um sistema que não existe mais. Isso não é preguiça do time — é consequência de um documento que nada consome.

📄 Documentação morta

  • Escrita depois do código
  • Ninguém a lê para produzir nada
  • Desatualiza em silêncio
  • Serve para prestar contas, não para construir
  • Custo puro, benefício difuso

⚡ Spec executável

  • Escrita antes do código
  • É o input do agente e do time
  • Desatualizar quebra o próximo ciclo — o erro aparece
  • Serve para construir e para verificar
  • Paga-se no primeiro retrabalho evitado

Por que agora?

Porque apareceu um leitor que consome a spec literalmente e produz código a partir dela. Um agente não infere o que "todo mundo sabe" sobre o produto: ele trabalha com o que está escrito. Isso transforma um documento antes opcional em combustível de produção.

"Executável" aqui não significa que a spec roda. Significa que alguém a executa — e esse alguém agora também é uma máquina.

O argumento econômico

O custo real de não usar SDD

Corrigir rumo é barato no começo e caro no fim. SDD não adiciona uma etapa — ele move a etapa de decisão para onde ela custa menos.

Onde o custo aparece na prática

⏱️

Tempo

Ciclos de "quase isso" que se acumulam durante o dia inteiro.

🧠

Contexto

Cada retomada obriga a reexplicar tudo — para o agente e para o colega.

👥

Revisão

Sem alvo escrito, o PR vira debate de opinião em vez de conferência.

🤝

Confiança

Ninguém sabe dizer se o que foi entregue é o que foi pedido.

O mesmo pedido, reescrito

Como isso muda o pedido na prática

Nada de burocracia: repare que a versão com spec não é mais longa por gosto — ela é longa exatamente onde havia uma decisão escondida.

pedido no chute
> faz um sistema de login pra mim

7 palavras. Pelo menos 5 decisões de produto deixadas em aberto, todas resolvidas por chute — e nenhuma delas registrada.

spec — autenticação por e-mail e senha
Objetivo Permitir que um usuário cadastrado acesse sua conta. Escopo · cadastro com e-mail + senha · login retornando um token de sessão · logout invalidando o token Fora de escopo · OAuth / login social · recuperação de senha (fica para o próximo ciclo) Critérios de aceite ✓ senha nunca é gravada em texto puro ✓ credencial errada retorna 401, sem dizer qual campo falhou ✓ token expira em 24h ✓ e-mail duplicado retorna 422 com mensagem clara

Agora existe um alvo verificável. Você não precisa ler o código para saber se a entrega está certa — basta conferir os quatro critérios.

Resumo da aula

🎯

O problema

Pedir código sem contexto transfere decisões de produto para o agente — em silêncio e sem registro.

🔄

A virada

A spec passa a ser a fonte da verdade; o código é artefato derivado dela.

⚡

Spec executável

Documentação morta é escrita depois e ninguém lê. A spec é escrita antes e é consumida para produzir.

💰

O custo

Corrigir na spec custa segundos; em produção, custa uma sprint. SDD move a decisão para o barato.
