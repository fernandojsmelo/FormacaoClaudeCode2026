Repare na proporção: quatro fases de pensamento para uma de código. Isso não é excesso de processo — é o reconhecimento de que escrever código nunca foi a parte difícil.

O princípio por trás

Separar o pensar do fazer

Quando pensamento e execução acontecem ao mesmo tempo, cada mudança de ideia desfaz trabalho já feito. Separá-los faz com que a mudança de ideia custe uma edição de texto.

Mudar de ideia é inevitável e saudável. O que o SDD faz é garantir que você mude de ideia enquanto o material ainda é barato.

Corrigindo um mal-entendido

O fluxo é iterativo, não linear

Olhando o diagrama, parece uma esteira: uma fase entrega para a seguinte e nunca se volta. Na prática, volta-se o tempo todo — e isso é o funcionamento normal, não uma falha.

Quando voltar para a spec

  • O plano revelou uma decisão de produto que ninguém tinha tomado
  • Um critério de aceite se mostrou impossível ou ambíguo
  • A implementação esbarrou numa regra de negócio não escrita
  • A verificação passou, mas o resultado não resolve o problema original

Quando voltar só para o plano

  • A abordagem técnica não sobreviveu ao contato com o código
  • Apareceu um caminho mais simples para o mesmo "o quê"
  • Uma dependência não existia ou se comportava diferente
  • A ordem das tarefas causava retrabalho evitável
🚩

Sinal de alerta: se você se pega discutindo o quê o sistema deve fazer durante a fase de implementação, pare. Isso não é um detalhe de código — é a spec pedindo para ser atualizada. Atualize-a e siga; não decida no meio do arquivo.

Waterfall também tem fases — a diferença é que lá voltar é um fracasso do processo. Aqui, voltar é o processo. A comparação completa vem na Aula F5.

Calibragem

Qual o tamanho certo de um ciclo?

A pergunta prática mais comum. A resposta curta: um incremento que você consegue verificar de uma vez.

Exemplo: "adicionar o campo descricao ao modelo".

Sintoma: a spec fica maior que a mudança. Você gasta mais tempo especificando do que teria gasto fazendo.

Ajuste: agrupe com o que vem junto, ou simplesmente faça — nem toda mudança precisa de spec. A Aula F5 traça essa fronteira.

Exemplo: "categorias: criar, listar e associar a cada transação, com filtro por categoria" — a Aula 3 do Projeto 1.

Sintoma de que está certo: cabe em 4 a 6 critérios de aceite; dá para demonstrar funcionando ao final; um commit (ou poucos) fecha o assunto.

📏

Régua prática: se você consegue enunciar o incremento em uma frase que contém um verbo e um resultado observável, o tamanho está bom.

Exemplo: "fazer o app de controle de gastos".

Sintoma: a spec vira um documento de produto; o plano tem trinta passos; a verificação não cabe numa sessão; e o contexto do agente satura no meio do caminho.

Ajuste: quebre por valor entregue, não por camada técnica. "Registrar e listar transações" é um bom corte; "fazer o banco de dados" não é — porque não dá para verificar sozinho.

O momento mais valioso do ciclo acima é o ✗ na fase 2: uma correção de rumo que custou uma frase. Se ela tivesse sido descoberta na fase 5, custaria uma reimplementação.

Resumo da aula

🔄

Seis fases

Princípios → especificar → planejar → tarefas → implementar → verificar. Cada uma com um artefato próprio.

🧠

Pensar ≠ fazer

Separar as duas coisas faz o descarte cair sobre texto, não sobre código já escrito.

↩️

Iterativo

Voltar à spec quando o rumo desvia é o processo funcionando, não falhando.

📏

Tamanho do ciclo

Um incremento verificável de uma vez: 4 a 6 critérios de aceite, demonstrável ao final.
