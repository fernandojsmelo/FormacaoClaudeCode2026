Explorando
os Widgets

Até aqui, os agentes respondiam com texto ou JSON. Widgets são componentes visuais do ChatKit (cartões, listas, botões, formulários) que aparecem dentro da conversa. Nesta aula, desenhamos no Widget Builder a Trilha de Estudo do curso, entendemos o que há dentro de um arquivo .widget, ligamos o widget ao agente pelo Output format e tratamos ações: botões que abrem links e um formulário que só age com confirmação.

Conceito01

Por que widgets

Uma lista de cinco aulas com título, módulo, motivo e link fica confusa em texto corrido. O mesmo conteúdo num cartão com linhas e botões é lido num relance e permite agir com um clique. Segundo a documentação, widgets são os contêineres e componentes do ChatKit: você pode usar os prontos, adaptar modelos ou desenhar os seus.

Saída do agenteBom paraLimite
TextoExplicações, conversasListas e comparações ficam difíceis de ler
JSON (aulas 02 e 05)Passar dados para outro nó ou para o seu códigoNão é feito para o usuário ler
Widget (esta aula)Mostrar dados estruturados e oferecer açõesSó aparece onde há ChatKit
O ponto-chave: o widget é um JSON com esquema que vira interface. Tudo o que você aprendeu sobre saída estruturada continua valendo; muda só quem lê o resultado.
As peças02

Contêineres e componentes

Todo widget tem um contêiner raiz (WidgetRoot) com vários componentes dentro (WidgetNode).

ContêinerCaracterísticas

ListViewLista vertical de ListViewItem, cada um clicável
BasicContêiner simples, sem moldura
GrupoComponentes
TextoTitle, Text, Caption, Markdown, Badge, Label
LayoutRow, Col, Box, Spacer, Divider, Table
MídiaImage, Icon
ControlesButton, Form, Input, Textarea, Select, Checkbox, RadioGroup, DatePicker
Pense em HTML com peças contadas: não há CSS livre nem script. Isso garante que o widget se ajuste ao tema do ChatKit (claro ou escuro) e seja seguro de exibir.

Passo 105

A view, em JSX

<Card size="md"> <Title value="Sua trilha de estudo" /> <Caption value={objetivo} /> <Divider flush /> {aulas.map((aula) => ( <Row key={aula.titulo} gap={3}> <Box background="#DE8B62" width={4} /> <Col flex={1}> <Text value={aula.titulo} weight="bold" /> <Caption value={aula.motivo} /> </Col> <Badge label={aula.modulo} /> <Button label="Abrir" variant="outline" onClickAction={{ type: "open.url", payload: { url: aula.url }, }} /> </Row> ))} <Divider /> <Text value={resumo} /> </Card>
As chaves

{objetivo}, {aulas} e {resumo} são os dados. A view só diz como mostrá-los; quem os fornece é o agente.

O laço

aulas.map(...) repete a linha para cada aula: 3 ou 5, o cartão se ajusta.

O botão

A ação open.url abre o link. É o mesmo tipo de ação usado no exemplo oficial do cookbook.

Passo 106

O esquema dos dados

{ "type": "object", "properties": { "objetivo": { "type": "string" }, "aulas": { "type": "array", "minItems": 3, "items": { "type": "object", "properties": { "titulo": { "type": "string" }, "modulo": { "type": "string" }, "motivo": { "type": "string" }, "url": { "type": "string", "format": "uri" } }, "required": ["titulo", "modulo", "motivo", "url"], "additionalProperties": false } }, "resumo": { "type": "string" } }, "required": ["objetivo", "aulas", "resumo"], "additionalProperties": false }

Junto da view, o widget carrega um JSON Schema dos dados. É ele que o agente vai seguir.

É o mesmo tipo de esquema das aulas 02 e 05. A diferença: em vez de você ler o JSON, o ChatKit o desenha.
minItems: 3 garante uma trilha de verdade; format: "uri" pede um link válido. Restrições no esquema evitam cartões vazios ou quebrados.
Por dentro07

O que há num arquivo .widget

O .widget baixado é um JSON. Abrindo o arquivo de exemplo publicado no cookbook da OpenAI, encontramos estes campos:

CampoO que guarda
version e nameVersão do formato e nome do widget
templateA estrutura do widget em JSON, com marcações de modelo para encaixar os dados (laços e variáveis)
jsonSchemaO esquema dos dados que o agente precisa produzir
outputJsonPreviewO widget já montado com os dados de exemplo
encodedWidgetO projeto do Widget Builder (incluindo a view em JSX), codificado
Não edite o .widget à mão: o formato não tem documentação própria. Mude no Widget Builder e baixe de novo. Guarde o arquivo no repositório do projeto, como guardaria qualquer fonte.

Ações10

Quando o usuário clica

Componentes interativos recebem uma ação (ActionConfig): um type, um payload e, opcionalmente, quem a trata (handler).

AçãoQuem trataExemplo
open.urlO próprio ChatKitO botão "Abrir" da trilha
Ação personalizada com handler: "client"O seu front-end, no callback widgets.onAction"Agendar" chama a API do seu site
Ação personalizada no servidorO seu servidor ChatKit (ChatKit Python SDK), que pode atualizar o widget ou responder na conversaSalvar a revisão e responder "Agendado!"
Com o workflow hospedado pelo Agent Builder, o caminho mais direto para ações próprias é o onAction no front-end, que repassa ao seu back-end, como no exemplo da documentação.
Compare com a aula 06: na client tool, o agente pede algo ao navegador; na ação de widget, quem dispara é o usuário, com um clique.
Passo 311

Tratar a ação no front-end

chatkit.setOptions({ api: { getClientSecret }, widgets: { async onAction(action, item) { if (action.type !== "agendar_revisao") return; // payload traz os campos do formulário, pelo name const { data, canal } = action.payload; const res = await fetch("/api/revisoes", { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ data, canal, itemId: item.id }), }); // avisa o servidor do ChatKit, se você tiver um await chatkit.sendAction( { type: "revisao_agendada", payload: { ok: res.ok } }, item.id, ); }, }, });
A assinatura

Pelos tipos do chatkit-js, o callback recebe a ação e o item do widget que a originou. sendAction envia uma ação ao servidor, opcionalmente ligada a esse item.

O payload vem do navegador, como o resultado de uma client tool: o seu back-end valida tudo de novo (data no futuro, canal permitido, usuário logado).
Formulários12

Coletar dados com confirmação

<Card size="sm" asForm confirm={{ label: "Agendar", action: { type: "agendar_revisao", handler: "client" } }} cancel={{ label: "Agora não", action: { type: "cancelar_revisao", handler: "client" } }}> <Title value="Agendar revisão" /> <Label value="Data" fieldName="data" /> <DatePicker name="data" /> <Label value="Canal" fieldName="canal" /> <Select name="canal" options={[ { value: "email", label: "E-mail" }, { value: "whatsapp", label: "WhatsApp" }, ]} /> </Card>
asForm

Com asForm, o Card se comporta como um Form: valida os campos e envia os valores para a ação de confirm.

O name vira chave

Cada campo entra no payload pelo seu name: data vira action.payload.data. Nomes repetidos colidem; use nomes únicos.

Nada acontece até o clique em Agendar: é o "ação visível pede um sim" das aulas 04 e 06, agora com formulário.
Boas práticas13

Widgets que ajudam

  • Um widget, uma ideia: trilha num cartão, agendamento em outro
  • Poucos itens por lista: ListView tem limit
  • Textos curtos: o widget não é lugar para parágrafos
  • Botões com verbo claro: "Abrir", "Agendar", "Agora não"
  • Cores que funcionam nos temas claro e escuro
  • alt em toda Image (acessibilidade)
  • Um texto curto fora do widget, para quem lê por notificação ou leitor de tela
  • Versão do .widget guardada junto do projeto
Links vêm do modelo. Uma URL num botão open.url pode ter sido inventada ou injetada. Instrua o agente a usar só links das fontes e, se puder, confira o domínio (aula 07).
Nada sensível no payload. Tokens e dados pessoais não vão em ações: o payload circula pelo navegador e pela conversa.
Depois de 30/1114

Widgets sem o Agent Builder

# No seu servidor ChatKit (ChatKit Python SDK) from chatkit.widgets import Card, Title, Text, Button from chatkit.actions import ActionConfig def cartao_trilha(trilha) -> Card: linhas = [ Button( label=f"Abrir: {a.titulo}", variant="outline", onClickAction=ActionConfig( type="open.url", payload={"url": a.url} ), ) for a in trilha.aulas ] return Card(children=[ Title(value="Sua trilha de estudo"), *linhas, Text(value=trilha.resumo), ]) # trilha = saída estruturada de um Agent do Agents SDK # (output_type com objetivo, aulas e resumo, como na página 06)
O que continua e o que muda
  • O ChatKit continua disponível: só o Agent Builder sai do ar em 30/11/2026
  • O agente vira um Agent do SDK com output_type igual ao jsonSchema do widget
  • O seu servidor monta o widget com os componentes do ChatKit Python SDK e o envia à conversa
  • Ações podem ser tratadas no servidor, além do onAction no cliente
O .widget continua útil como especificação: o esquema e a prévia dizem exatamente o que construir. Confira os nomes exatos dos componentes no guia do ChatKit Python SDK.
Armadilhas15

Erros comuns com widgets

Widget bonito com dado inventado. O visual passa confiança; a regra "só das fontes" é ainda mais importante.
Confiar no payload. Ele vem do navegador: valide no back-end, sempre.
Editar o .widget à mão. Formato sem documentação; mude no Widget Builder e baixe de novo.
Ação sem confirmação. Agendar, comprar e enviar pedem um botão de confirmar.
Testar só no tema claro. Cores fixas somem no escuro.
Esperar widget pela API pura. Widget é do ChatKit; sem ele, sobra só o JSON.

Recapitulando17

A aula em uma página

Widgets transformam a saída estruturada em interface: um contêiner (Card, ListView) com componentes de texto, layout e controle. Desenhamos a Trilha de Estudo no Widget Builder, vimos que o .widget guarda template, esquema e prévia, ligamos o arquivo ao agente pelo Output format e escrevemos instruções que dizem de onde vem cada campo.

Nas ações, open.url abre links; ações próprias chegam ao onAction; e um Card com asForm coleta dados e só age com confirmação, sempre com validação no back-end.
